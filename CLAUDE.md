# BMS_React-PyWeb — система керування бізнесом

Детальні правила розробки та контекст проєкту — у `.cursor/rules/*.mdc` (усі
`alwaysApply`). Пов'язаний проєкт — публічний каталог `BMS_catalog` (хмара: Neon + R2).

## ⛔ ЖОРСТКЕ ПРАВИЛО №1: НЕ перевищувати бюджет хмарних сервісів

Власник проєктів (BMS, BMS_catalog та всі інші) дозволяє на хмару **не більше $3 на
місяць** (Neon, план Launch лишається). Більше — ЛИШЕ з його явного дозволу. Будь-яке
списання понад бюджет — критичний інцидент. Це правило важливіше за швидкість/зручність
будь-якої фічі й діє для КОЖНОЇ зміни коду, яка прямо чи опосередковано звертається
до хмарного сервісу.

**Інцидент, через який правило з'явилось:** 01.10.2026 Neon списав 881.85 ₴ (≈$21)
за вересень. Причина — агент друку BMS опитував хмарний каталог кожні 5 с (+ пульс
кожні 30 с), кожен запит доходив до Neon, і compute не засинав жодної хвилини
(0.25 CU × 24 год × 30 днів ≈ 180 CU-год при ліміті 100).

### Neon (хмарна Postgres каталогу, проєкт `plain-breeze-73014199`)
- Бюджет: **$3 на місяць** (`NEON_BUDGET_USD`). Launch: compute $0.106/CU-год,
  зберігання $0.35/ГБ-міс. Тобто ≈ **25 CU-год на місяць** — робоча ціль ≤ 15 CU-год.
  Коли витрата сягає 90% бюджету, BMS **вимикає compute-ендпоінти через Neon API**
  (жорсткий запобіжник): база не прокинеться, доки власник не натисне в BMS
  «Дозволити ще $1» або не почнеться новий місяць.
- Compute засинає лише після **5 хв ПОВНОЇ тиші**. Один запит раз на <5 хв = база не
  спить ніколи. Кожне «пробудження» коштує ≈ 6 хв × 0.25 CU ≈ 0.025 CU-год.
- **Заборонено:** таймери/полінг/heartbeat/cron/keep-alive, що доходять до хмарної
  БД частіше ніж раз на ~30 хв у фоні; постійні пули з'єднань у хмарі (лише NullPool);
  «перевірочні» запити про всяк випадок; синк без змін у даних.
- **Обов'язково:**
  - часте опитування (агенти, вкладки, що оновлюються самі) відповідає з ПАМ'ЯТІ
    сервера каталогу (`BMS_catalog/backend/quiet_db.py`) або з локальної БД — не з Neon;
  - синк у хмару — лише коли змінились дані (відбиток у `cloud/sync_to_cloud.py`);
  - полінг у UI — лише коли вкладка видима (`document.hidden` → не опитувати);
  - у кожному коміті, що додає звернення до хмари, — оцінка: скільки пробуджень на
    добу × 6 хв × 0.25 CU = CU-год/міс × $0.106. Якщо > $0.50/міс — спершу узгодити з власником;
  - запобіжник (`NEON_HARD_CAP`) не вимикати і поріг не піднімати без дозволу власника.
- **Лічильник:** BMS читає витрату через Neon API (`NEON_API_KEY`, `NEON_PROJECT_ID`)
  і показує сповіщення. Ключ — **Org-wide** (проєктний отримує 403 на споживання). Витрата
  compute — з `/consumption_history/v2/projects` (метрика `compute_unit_seconds`, daily +
  hourly за сьогодні, потрібен `org_id`): поля проєкту `compute_time_seconds`/`cpu_used_sec`
  на платному плані завжди 0 (перевірено 03.10.2026) — на них покладатись НЕ можна. Рівні від бюджету:
  `warn` ≥ 60%, `economy` ≥ 75% (синк рідше), `stop` ≥ 90% (compute вимкнено; BMS і
  launchd-синк НЕ будять хмару; дозвіл власника — `POST /api/cloud-budget/permit`).
  Стан пишеться у `~/.bms/cloud_budget.json` — його читає `sync_to_cloud.py`.
- Max autoscaling = 0.25 CU. Не змінювати план, розмір compute і не вмикати платні
  опції без прямої згоди власника. Free-план (100 CU-год) теж підтримується: `NEON_PLAN=free`.

### Інші сервіси — так само лише безкоштовні ліміти
- Cloudflare R2: ≤ 10 ГБ, ≤ 1 млн операцій запису (Class A) і ≤ 10 млн читання (Class B) на місяць.
- Хостинг каталогу (Railway/Render), Google Sheets API, Telegram Bot API, OLX/Prom API —
  жодних платних тарифів/надбавок; квоти не вичерпувати циклами/полінгом.
- Нова хмарна послуга чи платна опція — **тільки з явної згоди власника**, з оцінкою вартості.

### Де це реалізовано в BMS
- `backend/services/cloud_budget.py` — бюджет Neon у $ (API), рівні, жорсткий запобіжник, дозвіл, файл стану.
- `backend/routers/cloud_budget.py` — `GET /status`, `POST /refresh`, `POST /permit` (`/api/cloud-budget/…`).
- `backend/routers/parsing.py` → `_trigger_catalog_cloud_sync` — синк лише з дозволу
  бюджету й не частіше за інтервал рівня (за замовчуванням ≥ 20 хв, debounce).
- `frontend/src/components/common/CloudBudgetBanner.tsx` — сповіщення й кнопка «Дозволити ще $1».
- `backend/scripts/neon_budget_guard.py` + `deploy/com.bms.neon-budget-guard.plist` — той самий
  запобіжник кожні 15 хв через launchd, навіть коли BMS закритий.
- **Статистика → «Сервери й хмара»** (`services/cloud_costs.py`, `routers/cloud_costs.py`,
  `components/statistics/CloudCostsPanel.tsx`): витрати цього місяця по сервісах (Neon,
  Railway, Cloudflare Workers/R2, AI-Gemini з `ai_budget`, ручні пункти) і по напрямах
  Каталог / Склад / BMS + усього, у $ і ₴ (курс НБУ). Лише білінгові API провайдерів (базу
  не будить), кеш оновлюється разом із лічильником Neon. Каталог і Склад ділять сервер і
  базу — частку задає власник (`~/.bms/cloud_costs_config.json`, правка на сторінці).
  Новий платний сервіс → додати провайдера в `PROVIDERS` (або ручним пунктом).
  Перевірка з терміналу (без секретів): `./venv/bin/python backend/scripts/cloud_costs_check.py`.
  ⚠️ Формат Railway/Cloudflare API звірено лише на фікстурах — при першому підключенні токенів
  прогнати цю перевірку й за потреби підправити запит/розбір (як це було з Neon).
